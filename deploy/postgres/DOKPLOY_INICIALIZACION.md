# Inicialización PostgreSQL en Dokploy

Esta guía es para una base **vacía**. No importa SQLite ni `state.json`; los usuarios y el historial anteriores no aparecerán. La ejecución en el entorno real y la conectividad de Dokploy no han sido verificadas. Conserve los volúmenes actuales y sus respaldos.

1. Configure la imagen API desde el contexto raíz del repositorio (`.`) y `Dockerfile`; el worker usa el mismo contexto y `Dockerfile.worker`. Conecte ambos servicios a la red privada en la que PostgreSQL resuelve su host; no exponga 5432 a Internet.
2. En Environment de la API y el worker configure `ConnectionStrings__DefaultConnection` con `Host=botsopa-botdb-tq5vhi;Port=5432;Database=bot_db;Username=admin_bot;Password=<PASSWORD>`. Configure la contraseña real solo en el gestor de secretos de Dokploy. En API configure `ASPNETCORE_ENVIRONMENT=Production`, `SRI_ADMIN_USERNAME`, `SRI_ADMIN_PASSWORD` (única, al menos 16 caracteres), `SRI_COOKIE_SECURE=true` y `Cors__AllowedOrigins__0=https://bot.dokploy.integritysolutions.com.ec`. El usuario inicial interno es `Cristopher`; `SRI_ADMIN_USERNAME` es su alias de login. El cambio posterior de `SRI_ADMIN_PASSWORD` no cambia su contraseña ya creada.
3. Mantenga y monte los volúmenes existentes de descargas, sesiones, credenciales y configuración. Preserve y configure las claves originales mediante `SRI_CREDENTIAL_KEY_FILE` o `SRI_CREDENTIAL_KEY_BASE64`, `SRI_SESSION_KEY_FILE` o `SRI_SESSION_KEY_BASE64`, y la clave del agente (`SRI_AGENT_KEY_FILE` o la variable correspondiente). Configure `SRI_OUTPUT_PATH`, `SRI_SESSION_PATH`, `SRI_CREDENTIAL_PATH`, `SRI_STATE_PATH` y `SRI_PORTAL_PROFILE` de acuerdo con los montajes. El worker necesita la misma conexión, acceso a descargas y sesiones, la clave de sesiones y `SRI_WORKER_PAUSED=true` hasta completar las comprobaciones. No use varios workers.
4. Cree una tarea o contenedor **efímero** con la imagen de la API, en la misma red y con las variables necesarias. Ejecute como argumento de la imagen `--db-migrate`; a continuación ejecute otra tarea con `--db-init` y `SRI_ADMIN_PASSWORD`. El ENTRYPOINT de la imagen ya es `dotnet SriAutomation.Api.dll`, por lo que no se debe añadir de nuevo `dotnet` como argumento. Equivalentes dentro de la imagen: `dotnet SriAutomation.Api.dll --db-migrate` y `dotnet SriAutomation.Api.dll --db-init`. Los comandos terminan antes de iniciar HTTP. La migración se puede repetir; `--db-init` no sobrescribe usuarios existentes.
5. Inicie la API y compruebe `https://botisc.dokploy.integritysolutions.com.ec/health/ready`: debe responder HTTP 200; 503 indica que no está preparada. Esta comprobación no prueba todas las operaciones de escritura. Verifique login, una lectura y escritura controladas y las asignaciones antes de activar el worker. Compruebe los permisos de los volúmenes y las claves sin revelar sus contenidos.

## Respaldo y restauración

Desde un cliente privado con `pg_dump`, `pg_restore` y `psql`, configure `PGHOST`, `PGPORT`, `PGDATABASE` y `PGUSER`; entregue la contraseña mediante `.pgpass` protegido o el mecanismo de secretos del entorno. No incluya la contraseña en los comandos. Genere un respaldo lógico consistente con `pg_dump --format=custom --file=bot_db.backup` y almacénelo cifrado fuera del host con acceso restringido. Respalde por separado descargas, credenciales, sesiones, configuración y claves; el dump no los contiene. Para una copia coherente entre base y archivos, detenga los procesos escritores durante la captura.

Ensaye la recuperación en una **base nueva aislada**: cree la base vacía con un administrador autorizado, ajuste `PGDATABASE` a ese nombre y ejecute `pg_restore --exit-on-error --no-owner --dbname="$PGDATABASE" bot_db.backup`. Compruebe tablas, conteos, login y acceso a archivos con las claves originales. Nunca restaure sobre una base activa sin un plan específico: detenga escritores, respalde primero el destino y valide la recuperación. Revertir a SQLite después de aceptar escrituras PostgreSQL requiere reconciliar esas escrituras para no perderlas.
