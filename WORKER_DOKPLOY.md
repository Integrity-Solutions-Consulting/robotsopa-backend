# Worker independiente en Dokploy

Esta preparación no crea ni modifica servicios. El repositorio remoto debe contener los cambios locales que se quieran desplegar; Dokploy construye la revisión de Git configurada, no los archivos locales sin confirmar.

1. Cree una aplicación nueva desde el repositorio backend y seleccione el proveedor y la rama que contengan la revisión deseada. Seleccione construcción Dockerfile, contexto `.` y Dockerfile `Dockerfile.worker`. No reutilice ni modifique la aplicación API.
2. Configure una sola instancia, reinicio automático y, si Dokploy ofrece esas opciones, `init` y memoria compartida de 1 GiB para Chromium. No configure dominio ni puerto: el Worker no escucha HTTP. El comando de la imagen es `dotnet SriAutomation.Worker.dll`; deje el comando vacío para usar su ENTRYPOINT.
3. Configure `ConnectionStrings__DefaultConnection` con la conexión a la misma base y esquema PostgreSQL de la API, con permisos de lectura y escritura. La aplicación debe alcanzar el host y puerto de esa conexión por la red privada existente; incluya la configuración TLS y certificados requeridos por esa conexión. No use `localhost` para referirse a otro contenedor.
4. Configure `SRI_WORKER_PAUSED=false`, `SRI_OUTPUT_PATH=/app/downloads`, `SRI_STATE_PATH=/app/storage`, `SRI_SESSION_PATH=/app/sessions` y `SRI_SESSION_KEY_FILE=/run/secrets/session-key`. El perfil incluido usa `SRI_PORTAL_PROFILE=/app/config/sri-portal.json`.
5. Monte los mismos volúmenes o rutas persistentes usados por la API para `/app/downloads`, `/app/storage` y `/app/sessions`, sin crear volúmenes vacíos por accidente. Compruebe lectura y escritura, y que ambos servicios usen el mismo contenido. El bloqueo de una sola instancia depende de `/app/storage/.worker.lock`; no active otra instancia con almacenamiento distinto.
6. Monte en `/run/secrets/session-key`, con acceso de lectura, la clave binaria original de sesiones de 32 bytes. Como alternativa use `SRI_SESSION_KEY_BASE64` con los mismos 32 bytes codificados; esa variable prevalece sobre el archivo si está presente, incluso vacía. No cambie ni regenere una clave existente. El perfil está en la imagen; si la API usa un perfil personalizado, monte ese mismo archivo en la ruta configurada.
7. Para SharePoint, configure `SRI_SHAREPOINT_ENABLED=true`, `SRI_SHAREPOINT_TENANT_ID`, `SRI_SHAREPOINT_CLIENT_ID`, `SRI_SHAREPOINT_SITE_ID`, `SRI_SHAREPOINT_DRIVE_ID` y `SRI_SHAREPOINT_CLIENT_SECRET` o `SRI_SHAREPOINT_CLIENT_SECRET_FILE`; `SRI_SHAREPOINT_FOLDER` es opcional. En caso contrario configure `SRI_SHAREPOINT_ENABLED=false`.
8. Tras validar la configuración, despliegue únicamente esta nueva aplicación. Revise logs de acceso al almacenamiento, conexión PostgreSQL y `Worker activo`. Consulte autenticado `GET /api/v1/worker/status` en la API: `online` debe ser `true` y `heartbeat` reciente. El healthcheck de la imagen requiere heartbeat de menos de 30 segundos; la API usa 15. Un heartbeat prueba conectividad y actividad del proceso, no una descarga completa.
9. Para una prueba funcional, use un trabajo controlado y autorizado desde la interfaz. Compruebe su transición de pendiente a ejecución y resultado, los mensajes, y los archivos/reportes o entrega. Las operaciones SRI pueden requerir el agente Windows conectado y verificación humana. No declare éxito solo por ver el heartbeat.

El arranque ejecuta `PostgresAdministration.Verify`, que comprueba esquema y estado existentes sin migrar. Tras arrancar, el Worker sí modifica la cola, heartbeat y estados existentes, y recupera trabajos `Running`; revise cualquier trabajo pendiente antes de habilitarlo. No ejecute `--db-init` ni `--db-migrate` para instalar el Worker. El procesamiento requiere PostgreSQL, acceso de salida al SRI y, si se habilita, a Microsoft Graph.
