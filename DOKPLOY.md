# BotSopa: backend en Dokploy

Repositorio: `robotsopa-backend`; Docker Compose `./compose.dokploy.yml`, contexto raíz. Un solo host, una API y un worker. No configure dominio ni puertos públicos para estos servicios. La API escucha internamente en 8080 y el worker no escucha un puerto. `SRI_WORKER_PAUSED` por defecto es `true`; manténgalo así para el primer despliegue. El indicador saludable en pausa no significa procesamiento activo.

En Dokploy v0.30.10, antes de desplegar cree una red externa attachable `botsopa-sri-network` en el servidor, por ejemplo `docker network create --driver overlay --attachable botsopa-sri-network` en el host Swarm de Dokploy; confirme con `docker network inspect botsopa-sri-network` que sea attachable y que ambos Compose corran en el mismo host. Si el servidor no usa Swarm, use `docker network create --driver bridge botsopa-sri-network` en ese host. Seleccione Docker Compose, no Stack. La API tiene el alias único `botsopa-sri-api`; no reutilice esa red ni ese alias en otra instalación. En la gestión de redes por servicio de v0.30, conserve esta red en `api` y retire `dokploy-network` de `api` y `worker`; `worker` mantiene la red privada predeterminada de su Compose. En `front` conserve la red compartida y `dokploy-network` para Traefik. No habilite la opción heredada Isolated Deployments. Revise Preview Compose antes de desplegar y confirme las conexiones reales posteriormente: no se dispone de acceso al servidor desde este entorno.

En Environment del backend configure `SRI_ADMIN_USERNAME`, `SRI_ADMIN_PASSWORD` (mínimo 16 caracteres), `SRI_CONFIG_DIR` y `SRI_SECRET_DIR` como rutas absolutas del host; opcionalmente `SRI_WORKER_PAUSED=true`. Dokploy guarda su Environment como .env en el servidor: restrinja el acceso. La contraseña solo inicializa el administrador si no existe hash; no reemplaza contraseñas existentes. `SRI_COOKIE_SECURE=true` se fija en Compose para HTTPS; la API no confía en X-Forwarded-Proto. Conserve HTTPS obligatorio en el frontal.

Coloque en `SRI_CONFIG_DIR/sri-portal.json` el perfil existente del proyecto; este perfil no está validado contra el SRI. En `SRI_SECRET_DIR` conserve `agent.key`, `credential.key` y `session.key` originales, con directorio 700 y archivos 600, propiedad accesible a los contenedores. Solo en una instalación vacía pueden generarse claves nuevas: `openssl rand -hex 32 > agent.key`, `openssl rand 32 > credential.key`, `openssl rand 32 > session.key`. No regenere claves al migrar. Los montajes son de solo lectura y fallan si faltan rutas. Las imágenes actuales ejecutan como root; endurecimiento y comprobación de permisos siguen pendientes.

Los volúmenes locales de Compose `state`, `sessions`, `downloads` y `credentials` persisten entre reconstrucciones. API y worker comparten los tres primeros; credentials pertenece a API. `state` contiene `panel.db` y auxiliares SQLite, `state.json` y respaldo. Use nombre de proyecto Compose estable; identifique los nombres reales con `docker volume ls` antes de migrar. No use `down -v`, no use almacenamiento de red ni ejecute dos workers contra el mismo estado. Mantenga usuarios, roles, hashes, asignaciones RUC e historial copiando el conjunto completo, sin reinicializar ni ejecutar scripts de reseteo.

## Orden y recuperación

1. Detenga escrituras y API, worker y agente de origen; respalde de manera consistente los cuatro volúmenes, configuración y claves originales (claves cifradas en copia separada). Incluya WAL/SHM SQLite si existen. No modifique los datos de origen.
2. Ensaye la restauración completa en un entorno aislado, sin acceso al SRI y con worker pausado. Restaure volúmenes y claves como conjunto, confirme propietarios/permisos y valide usuarios, roles, asignaciones e historial con datos de prueba. No mezcle versiones de base y estado. Para volver atrás restaure código y respaldo anterior completo.
3. Cree red, rutas, perfil y claves en servidor; configure y despliegue backend pausado. Revise salud API y registros sin revelar secretos. Configure y despliegue frontend y TLS según su guía.
4. Verifique HTTPS, cookie Secure, login, permisos por RUC e historial individual, reinicios independientes y persistencia. Un reinicio de API invalida sesiones del panel. Verifique restablecimiento del proxy tras recrear API. Mantenga la pausa hasta aprobar trabajos pendientes y validar el entorno. No ejecute consultas reales durante estas pruebas.
